GET Filter, order & paginate

First-class filtering (eq / gte / lte / neq / like / in), ordering, limit/offset pagination, and column (vertical) selection — all in the URL. Here: critical work orders, newest first.

How this works
The call
GET /field_service/work_orders?select=work_order_id,status,priority,created_at&priority=eq.critical&order=created_at.desc&limit=10&offset=0
+ header Prefer: count=exact  ·  schema / table / query params
The idea The URL is the query. PostgREST turns each query-string param into SQL: select= picks columns, priority=eq.critical is a WHERE filter (operator eq), order= sorts, limit/offset page. Prefer: count=exact asks the server for the exact total, returned in the Content-Range header — which is why a page comes back as 206 Partial Content.
Equivalent SQL
SELECT work_order_id, status, priority, created_at
FROM   field_service.work_orders
WHERE  priority = 'critical'
ORDER  BY created_at DESC
LIMIT 10 OFFSET 0;
offset 0

GET Multi-table join & hierarchical

FK resource embedding returns nested related rows in a single request — work orders with their customer and appointments — via ?select=…customers(…),appointments(…). That's your nested/hierarchical retrieval.

How this works
The call
GET /field_service/work_orders?select=work_order_id,status,priority,customers(first_name,last_name,region_id),appointments(scheduled_start,status)
The idea Resource embedding. Naming a related table inside select=…customers(…) tells PostgREST to follow the foreign keys from work_orders → customers and → appointments, and nest those rows in the JSON — one request, no client-side joins.
Equivalent SQL
SELECT wo.work_order_id, wo.status, wo.priority,
       c.first_name, c.last_name, c.region_id,   -- nested customers(…)
       a.scheduled_start, a.status               -- nested appointments(…)
FROM   field_service.work_orders wo
LEFT JOIN field_service.customers    c ON c.customer_id   = wo.customer_id
LEFT JOIN field_service.appointments a ON a.work_order_id = wo.work_order_id
ORDER BY wo.work_order_id LIMIT 5;

POST /rpc Aggregation

Aggregations aren't in the PostgREST select grammar — the recommended pattern is a SQL SETOF function / view exposed as an RPC. Here: /rpc/sla_compliance_by_region (GROUP BY region).

How this works
The call
POST /public/rpc/sla_compliance_by_region  body {}
The idea The select grammar has no GROUP BY. So the aggregation lives in a Postgres function and you call it at /rpc/<name> (/public = schema, /rpc = the function-call namespace). The JSON body carries function args — none here.
Function body (SQL)
SELECT sr.region_name,
       COUNT(*)                       AS completed_orders,
       COUNT(*) FILTER (WHERE sla_met) AS sla_met_orders,
       ROUND(100.0 * COUNT(*) FILTER (WHERE sla_met)
             / NULLIF(COUNT(*),0), 1)  AS compliance_pct
FROM   field_service.work_orders wo
JOIN   field_service.service_regions sr ON sr.region_id = wo.region_id
WHERE  wo.status = 'completed'
GROUP  BY sr.region_name
ORDER  BY compliance_pct DESC;

POST /rpc Nested subquery + JOIN

Complex/nested queries (CTE + JOIN + window function) live in a function, called via /rpc/. Here: top-N technicians per region by completed work orders.

How this works
The call
POST /public/rpc/top_technicians_by_completions  body {"n": 5}
The idea Same RPC pattern for a genuinely complex query: a CTE counts completions per technician, then a ROW_NUMBER() window ranks them within each region. The JSON body {"n":5} maps to the function's n argument (top-5 per region).
Function body (SQL)
WITH tech_completions AS (          -- served by a partial index on completed WOs
  SELECT assigned_technician_id AS technician_id, COUNT(*) AS completions
  FROM   field_service.work_orders
  WHERE  status = 'completed' AND assigned_technician_id IS NOT NULL
  GROUP  BY assigned_technician_id
), ranked AS (
  SELECT t.technician_id, t.first_name||' '||t.last_name AS tech_name,
         sr.region_name, COALESCE(tc.completions,0) AS completions,
         ROW_NUMBER() OVER (PARTITION BY t.region_id
                            ORDER BY COALESCE(tc.completions,0) DESC) AS region_rank
  FROM   field_service.technicians t
  JOIN   field_service.service_regions sr ON sr.region_id = t.region_id
  LEFT JOIN tech_completions tc ON tc.technician_id = t.technician_id
)
SELECT * FROM ranked WHERE region_rank <= 5 ORDER BY region_name, region_rank;

GET Large result sets

Handle millions of rows: page with limit/offset and get the total in the Content-Range header via Prefer: count=estimated (planner estimate — instant, the right call on huge tables; count=exact is a full scan) — then watch an unbounded pull hit the API's ~10 MB response cap (HTTP 400). Pagination is the pattern.

How this works
Three calls
GET /field_service/work_orders?select=work_order_id&limit=1000 → 206 (a cheap page)
POST /public/rpc/work_orders_estimate → ~5.2M (planner estimate, instant)
GET …?limit=1000000 → 400 response is too large (max is 10485760 bytes)
The idea For millions of rows: page with limit/offset, and get the total from the planner's statistic (pg_class.reltuples) via a tiny RPC — instant at any table size. An exact count(*) over 5M rows is a full scan that can exceed the API's ~8s timeout on a cold endpoint, so it's the wrong tool at scale. An unbounded pull trips the ~10 MB response cap, so pagination is required.
Equivalent SQL
SELECT work_order_id FROM field_service.work_orders LIMIT 1000;   -- the page
SELECT reltuples::bigint FROM pg_class                            -- the total (no scan)
WHERE oid = 'field_service.work_orders'::regclass;

POST / PATCH / DELETE Bulk read/write

Bulk write via POST (insert an array), PATCH (+filter), DELETE (+filter). Runs against a public.data_api_demo sandbox — production is never touched. Inserts 3 rows, bulk-updates, then deletes them (self-resetting).

How this works
Three calls
POST /public/data_api_demo  body [{label,value}×3] → 201
PATCH /public/data_api_demo?label=like.bulk-*  body {value:999} → 200
DELETE /public/data_api_demo?label=like.bulk-* → 200
The idea One POST with a JSON array inserts many rows at once. PATCH and DELETE act on every row matching the URL filter (same eq/like/in grammar as GET), so ?label=like.bulk-* targets just our demo rows. Sandbox only — field_service is never touched.
Equivalent SQL
INSERT INTO public.data_api_demo (label,value) VALUES ('bulk-1',100),('bulk-2',200),('bulk-3',300);
UPDATE public.data_api_demo SET value = 999 WHERE label LIKE 'bulk-%';
DELETE FROM public.data_api_demo            WHERE label LIKE 'bulk-%';

Capabilities & limitations

Straight answers to the common questions, backed by the Data API docs.

QuestionData API answer
Multi-table joinsFK resource embedding (select=…child(…)); complex/ambiguous joins via a view or RPC function
Large result setslimit/offset pagination + exact count via Prefer: count=exact (Content-Range); ~10 MB response-size cap (paginate past it)
Aggregations / analyticalNot in the select grammar — expose a SETOF function / view, call via /rpc/
Nested subquery + JOINsEncapsulate in a view/function, call via /rpc/
Nested / hierarchicalNested embedding: select=customers(work_orders(appointments(…)))
Pagination & filteringFirst-class: limit/offset, order, eq/gte/lte/neq/like/in; row access via RLS
Bulk read/writeGET + filters; POST (array) / PATCH (+filter) / DELETE (+filter)

Limitations & recommended patterns

  • Auth is Databricks OAuth (each identity → a PG role); no JWT config, GUCs, pre-request functions, or trace headers.
  • Only the public schema is exposed by default; others (e.g. field_service) must be explicitly exposed.
  • Enforce row-level security for multi-tenant access; RLS on views needs security_invoker.
  • FK auto-embedding can be ambiguous on partitioned tables / views with UNIONs — use computed relationships or RPC.
  • For heavy analytical scans, push aggregations into RPC functions, materialized/synced tables, or run them in the lakehouse / Databricks SQL — Lakebase is the OLTP layer.
  • Per-workspace rate/concurrency limits aren't publicly documented — confirm with your Databricks account team for strict SLAs.
